### 軸 2: asia1 の CPU（署名と JPEG の検証）をもっと軽くする

16:31 のベンチ（`logs/bench-20261031-163136/isucon2026-asia1/cpu.pprof`）のピークでは asia1 の CPU の idle が 0〜20%。内訳: 画像署名 `imageSignature` 33%（99% は URL を発行する側 `signedImageURL`。フィード・Memories の RealMoji・エクスポート）、投稿の JPEG の検証 `jpegcheck.Validate` 29%、`listMemories` 21%、エクスポート 12%、検索 7%、GC 2.4%。asia2（DB）もピークで idle 5〜15% なので、asia1 だけ軽くしても DB が次に詰まる可能性がある

制約（すでに試したこと）:
- 署名の計算方法・回数（HMAC-SHA256 × 1000）は変えられない（#9 で FAIL）。ベンチマーカーは自分でも署名して照合する
- exp は「今 + 24 時間」を 60 秒単位に切り上げ。上限の許容は 1〜15 分の間（#13〜#15 で FAIL）。**下限（切り下げ）は未確認**。切り下げが許されれば刻みを広げてキャッシュの当たりを増やせるが、確かめるには FAIL のおそれがある実験が要る
- 署名のキャッシュは (鍵, 画像 ID, exp) ごと。exp が 60 秒ごとに変わるので、毎分すべての画像を署名し直している
- JPEG はハフマン復号まで必要（エラーの判定を変えないため）。画素の復元は #18 で省いた
- 不正な署名の 403 の経路はすでに安い（画像データを読まない、署名の計算も最大 12 回）。CPU の 0.3%

検討の候補:
- 署名の計算を速くする: 今は Go の crypto/hmac + sha256（AVX2、SHA-NI は無い CPU）。HMAC の内側・外側の状態を前計算して、1 回あたり SHA-256 の圧縮 2 回だけにする（今は Reset と Sum の手間が約 25%）。AVX-512 があるので、複数の署名をまとめて計算する（マルチバッファ）実装なら数倍になりうるが大きい
- 分散: asia のユーザーのリクエストはルーターが asia1 に送るので、署名や JPEG の検証を europe1 / america1 に任せるにはサーバー間の新しい経路が要る（リージョンをまたぐので遅延と帯域制限もかかる）。**作る前にユーザーに確認**（CLAUDE.md、Clar #55）。europe / america のユーザーの署名は、もともとそれぞれのサーバーで計算している
- 署名の前計算: 次の 60 秒の exp の署名を、負荷の谷で先に作っておく（CPU の総量は減らないが、ピークをならせる）
